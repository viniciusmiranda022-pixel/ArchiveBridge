## Limitações conhecidas deste Passo (não fabricadas, documentadas explicitamente)

- **Worker hardening baseline:** nenhuma medição REAL de host Windows existe neste ambiente (sandbox de
  desenvolvimento/CI, sem workers reais provisionados) — todos os 12 controles da baseline permanecem
  `NotMeasured` neste Passo, exceto quando um teste constrói explicitamente uma
  `WorkerHardeningMeasurement` sintética para provar o mecanismo. `MdeTenantPolicyEnforcement` é
  `Unsupported` por design (Azure-only, sem capability comprovada on-premises) e nunca poderá ser `Pass`
  nesta baseline sem uma revisão que introduza a capability real.
- **WDAC/App Control:** este Passo entrega apenas o MODELO de evidência/validação — nenhuma policy é
  gerada/compilada/aplicada a nenhum host Windows real (nenhum `.cip`/binário de policy WDAC é produzido).
- **Supply-chain:** `BuildProvenanceRecord`/`ArtifactPromotionVerifier` são modelo de evidência/verificação
  em memória — nenhuma integração com o pipeline de CI real (GitHub Actions) foi conectada para aprovar
  builds automaticamente; isso permanece um incremento futuro.
- **Incident-response:** os 3 drills são sintéticos e determinísticos sobre o banco de teste efêmero — não
  substituem um exercício de IR real com stakeholders humanos (fora do escopo executável deste Passo).
- **Pen-test:** nenhum pen-test independente/institucional foi realizado — `PenTestReadinessBundle` só
  documenta preparação interna (`NotPerformed`/`Blocked`); permanece pendente para I8 ou incremento
  dedicado.
- **Simplificação de schema:** diferente do padrão de 0038/0040 (tabela principal + `*_audit_events`
  companheira), a migration 0041 usa UMA tabela por área — cada linha append-only já é, por si só, o
  evento auditável (mesmos campos de ator/timestamp/correlação que uma trilha dedicada teria). Reduz o
  número de tabelas de 10 para 5 nesta migration, mantendo o Passo no escopo de
  evidência/domínio/persistência pedido.
- **RLS em todas as 5 tabelas:** diferente do que a pesquisa preliminar do work order sugeria ("evidência
  de plataforma/build não precisaria de `TenantScope`"), esta implementação escopa TODAS as 5 tabelas por
  tenant/projeto — decisão deliberada para seguir o padrão dominante e já revisado do restante do schema
  (toda tabela existente tem `tenant_id`/`project_id` e RLS, inclusive `performance_benchmark_runs`, que é
  tão "de plataforma" quanto worker hardening/WDAC/build provenance). Isso também permite demonstrar a
  regressão de cross-tenant denial contra qualquer uma das 5 tabelas novas, não apenas uma.

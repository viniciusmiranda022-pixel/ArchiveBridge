# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-4C-005

## Slice 4C — Passo 2: Enterprise Vault Export Command & Throttling Foundation

## Objetivo

Avançar o I4 / EPIC-05 após enrollment/inventory, implementando a fundação segura e auditável para **export commands, thread throttling e captura de resultados do exporter Enterprise Vault**, conforme `docs/runbook/03-parte-iii-conectores-e-engine-pst.md` §16.3–16.4 e `docs/runbook/06-parte-vi-plano-desenvolvimento.md` EPIC-05.

O connector continua outbound-only. A execução deve permanecer atrás de adapters substituíveis; Domain/Application não podem depender de PowerShell/EV/vendor. Nenhuma execução contra ambiente real de cliente é autorizada por este work order sem capability/support-matrix certificada e host explicitamente autorizado.

## Fontes de autoridade

- `docs/runbook/03-parte-iii-conectores-e-engine-pst.md`, §§15, 16.1, 16.3 e 16.4;
- `docs/runbook/06-parte-vi-plano-desenvolvimento.md`, I4 / EPIC-05;
- Slice 4C Passo 1 mergeado no PR #37;
- ADRs, threat model, tenancy/custody/audit invariants e migrations policy vigentes.

## Escopo obrigatório

1. Definir contratos Domain/Application para pedido, tentativa e resultado de export EV, com identidade opaca e tenant/project/connector/archive scoped.
2. Implementar política validada de exportação com `MaxPstSizeMb` no intervalo documentado 500–51200 MB e default 18432 MB.
3. Implementar `MaxThreads` com intervalo documentado 1–32, porém sujeito a policy/capability do connector; não permitir override acima do envelope aprovado.
4. Implementar scheduler/throttling por connector e archive para impedir concorrência não autorizada e duplicidade de efeitos.
5. Implementar idempotência por identidade canônica do export request; retry do mesmo request deve convergir para a mesma operação lógica, preservando attempt history.
6. Criar adapter substituível para o exporter EV. A implementação concreta de processo/PowerShell deve ficar em Infrastructure/Connector Host e nunca atravessar Domain/Application.
7. O comando concreto deve seguir a forma documentada de `Export-EVArchive` com `-ArchiveId`, `-OutputDirectory`, `-Format PST`, `-MaxThreads`, `-MaxPSTSizeMB` e `-Retry`; argumentos devem ser construídos sem command injection e sem interpolação insegura de shell.
8. Antes de executar, validar capability handshake/support matrix do Passo 1: capability de export ausente, schema desconhecido, snap-in indisponível ou connector revogado devem bloquear fail-closed.
9. Output directory deve ser resolvido server-side sob a raiz local autorizada do connector; rejeitar traversal, UNC não allowlisted, symlink/junction/reparse point e escape de containment conforme runbook §15.2.
10. Capturar resultado do exporter de forma estruturada: exit/status, timestamps, attempt, arquivos PST encontrados, tamanho e SHA-256 de cada output após fechamento; não confiar em nome de arquivo como identidade.
11. Persistir export result/attempt history append-oriented e auditável. Evidência anterior não pode ser reescrita silenciosamente.
12. Produzir manifesto canônico dos PSTs exportados com identidade, tamanho, hash, engine/connector version e lineage para archive/request/attempt.
13. Revalidar outputs antes de aceitar replay como sucesso; arquivo ausente, hash divergente ou manifesto inconsistente deve falhar fechado.
14. Implementar classificação de oversized native items conforme §16.4: registrar vínculo/diagnóstico e direcionar estado lógico para `OversizedItem`; não omitir itens >250 MB / >2 GB.
15. Não persistir conteúdo de mailbox, subject/body/attachment, credencial EV, token, private key ou transcript bruto no Control Plane.
16. Transcript/log local, quando existir, deve ficar protegido no host connector e ser sanitizado antes de qualquer metadado enviado ao Control Plane.
17. Adicionar custody/audit events para requested, started, throttled, retry, completed, failed, output-discovered, oversized-detected e integrity-failed.
18. Aplicar anti-IDOR/cross-tenant/cross-project em todos os stores/use-cases/read models novos.
19. Migrations somente aditivas, determinísticas e com grants least-privilege; migrations anteriores byte-for-byte inalteradas.
20. Atualizar threat-model delta, runbook operacional do export connector e data classification.

## Acceptance criteria mínimos

1. Export não inicia se connector/export capability não estiver certificado/permitido.
2. `MaxPstSizeMb` e `MaxThreads` obedecem limites documentados e policy efetiva.
3. Concorrência acima do limite por connector/archive é bloqueada ou enfileirada deterministically; não duplica export lógico.
4. Retry do mesmo request preserva identidade lógica e registra attempts distintos sem sobrescrever evidência anterior.
5. Argumentos do processo não são vulneráveis a shell/PowerShell command injection.
6. Output path permanece contido na raiz autorizada e rejeita traversal/reparse/UNC não permitido.
7. Cada PST de saída aceito possui tamanho + SHA-256 calculados após fechamento e manifesto canônico persistido.
8. Replay de export concluído revalida integridade física; tampering/ausência/hash divergente falha fechado.
9. Oversized native item é materializado como exceção/estado explícito e nunca desaparece do evidence chain.
10. Domain/Application permanecem independentes de PowerShell/EV/vendor.
11. Nenhum segredo ou conteúdo de mailbox aparece em logs/evidence/control-plane persistence.
12. Cross-tenant/cross-project/forged connector/archive IDs são negados sem revelar existência.
13. CI completo verde no HEAD final.

## Testes obrigatórios

- policy boundaries 499/500/18432/51200/51201 MB;
- `MaxThreads` 0/1/default/32/33 e policy cap menor que request;
- capability unsupported/revoked/snap-in unavailable => fail-closed;
- duplicate concurrent request => um efeito lógico;
- throttle por connector e archive;
- retry após falha transitória preserva lineage/attempt history;
- command-argument injection corpus (`;`, quotes, backticks, pipes, CR/LF, `$()` etc.);
- path traversal, UNC, symlink/junction/reparse point e root escape;
- manifest deterministic + hash/tamanho;
- replay com output removido/adulterado => fail-closed;
- oversized native item materializado;
- SQL real para idempotência/concorrência/evidence quando aplicável;
- architecture tests provando ausência de dependência PowerShell/EV em Domain/Application;
- migration hashes anteriores estáveis;
- gitleaks/SCA/SBOM/format/build/test gates do repositório.

# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I7-001

## I7 — Hardening — Passo 1: Resilience, Recovery & Chaos Gates

## Fonte de autoridade

Este incremento implementa o primeiro bloco do I7 documentado em `docs/runbook/06-parte-vi-plano-desenvolvimento.md`, onde **I7 - Hardening** exige `HA, DR, chaos, performance, WDAC, pen-test, SLO`, e a estratégia de testes exige casos de `chaos`, `recovery`, `security` e `performance`. Respeitar também os ADRs aceitos, o runbook seguro on-premises e as invariantes já implementadas nos I0–I6.

A baseline vigente continua **on-premises**: SQL Server local, workers Windows Services, storage local/NTFS/NAS/SMB e Microsoft 365 apenas como destino externo. Não introduzir Azure PaaS/Service Bus/Key Vault como dependência obrigatória. O perfil HA de segredos permanece `BLOCKED_PENDING_EVIDENCE`.

## Objetivo

Transformar os principais cenários documentados de crash/recovery/ambiguidade em **gates automatizados de hardening** e fechar lacunas transversais de recuperação que possam permitir duplicidade de efeito, perda de evidência ou falso sucesso. Este Passo não declara Production Ready; ele produz evidência executável para os gates posteriores de I7/I8.

## Escopo obrigatório

1. Criar/organizar um harness de fault injection determinístico para testes de integração, sem alterar contratos de domínio apenas para facilitar testes.
2. Cobrir, no mínimo, os cenários documentados aplicáveis à arquitetura atual:
   - worker encerrado durante escrita/commit de artefato;
   - falha após hash e antes do custody/evidence state update;
   - lease expirando com worker ainda vivo;
   - SQL indisponível após efeito externo confirmado/possível e antes do state update;
   - entrega/reexecução duplicada de comando/job;
   - SAS expirando durante upload;
   - DNS/rede indisponível ou timeout transitório;
   - scratch/storage sem espaço ou escrita incompleta;
   - sink de log/telemetria indisponível;
   - provider retornando 429/5xx/resultado ambíguo;
   - identidade/permissão removida durante operação;
   - arquivo origem/output mudando durante processamento.
3. Para qualquer operação com efeito externo, provar por teste que estado ambíguo **não** dispara repetição automática cega; deve convergir para estado explícito de recuperação/reconciliação conforme a arquitetura vigente.
4. Provar fencing de lease/owner/epoch nos caminhos duráveis existentes: owner antigo não pode checkpointar, concluir, liberar ou publicar evidência depois de perder o lease.
5. Provar crash consistency dos artefatos/evidências: arquivo parcial, sidecar ausente, manifest/hash divergente ou commit SQL incompleto nunca pode ser reidratado como sucesso canônico.
6. Provar idempotência sob replay concorrente para os principais comandos de I4–I6 já implementados, sem duplicar efeitos externos, certificates, mappings, uploads ou evidências.
7. Adicionar testes de recovery para restart do processo/worker usando apenas estado durável; nenhum singleton/cache/memória local pode ser necessário para reconstruir estado autoritativo.
8. Revisar os principais `catch`/retry paths dos workers/adapters e corrigir apenas gaps comprovados pelos testes, preservando erros estáveis, sanitização e fail-closed.
9. Produzir uma matriz versionada de `failure mode -> expected state -> automatic action -> human action -> evidence`, ligada aos testes automatizados correspondentes.
10. Produzir documentação de recovery runbook para os estados realmente existentes no produto (`RECOVERY_REQUIRED`, `RECONCILING`, quarantine/DLQ ou equivalentes vigentes), sem inventar novos estados quando os existentes bastarem.
11. Manter observabilidade sanitizada: fault injection não pode fazer segredo, SAS, Authorization, mailbox/UPN sensível, UNC real ou conteúdo PST aparecer em logs/test output.
12. Executar todos os gates do repositório: restore locked, build Release warnings-as-errors, suíte completa com SQL Server real, architecture tests, format, SCA/SBOM, gitleaks/secret scanning e validação documental.

## Acceptance criteria

1. Cada cenário de chaos/recovery implementado possui assert explícito de que o sistema não duplica efeito, não perde evidência e não declara sucesso indevido.
2. Cenários de ambiguidade externa convergem para estado recuperável/reconciliável e nunca para retry automático destrutivo.
3. Fencing rejeita qualquer mutação de owner/epoch stale.
4. Crash/restart reconstrói o estado exclusivamente a partir de SQL + artefatos/evidências duráveis.
5. Tampering/partial writes nos artefatos cobertos falham fechado.
6. Replays concorrentes convergem deterministicamente sem registros canônicos duplicados.
7. A matriz de failure modes referencia testes automatizados reais e os runbooks usam apenas estados/códigos realmente existentes.
8. Nenhum segredo/PII sensível aparece nos logs, exceptions ou snapshots de teste.
9. CI oficial fica 100% verde.

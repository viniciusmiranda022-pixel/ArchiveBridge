# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I8-001

## I8 — Production Acceptance — Passo 1: Production Readiness Review & Gate Aggregation

## Objetivo

Iniciar o I8 consolidando, de forma executável e tamper-evident, o **Production Readiness Review** documentado no runbook antes de qualquer canário ou go-live. Este Passo deve agregar evidências já produzidas pelos incrementos anteriores e derivar um estado de readiness fail-closed para os gates de arquitetura, segurança, dados, operação e Microsoft 365. Não é permitido fabricar evidência ausente nem converter `Blocked/NotMeasured/NotPerformed` em `Pass`.

## Fontes de autoridade

- `docs/runbook/06-parte-vi-plano-desenvolvimento.md` §§43.2, 47, 48 e 49;
- roadmap/ADRs/threat models/governança já aceitos;
- evidências e modelos produzidos nos PRs #49–#52 do I7;
- cadeia canônica de reconciliation/certificate do I6;
- capability registry e evidence chain dos increments anteriores.

## Escopo obrigatório

1. **Readiness gate model**
   - modelar os cinco grupos documentados do §47: `Architecture`, `Security`, `Data`, `Operations` e `Microsoft365`;
   - cada controle deve possuir identidade estável, status explícito (`Pass`, `Fail`, `Blocked`, `NotMeasured`, `NotPerformed` quando aplicável), evidence references opacas e reason/code sanitizado;
   - o resultado agregado só pode ser `ReadyForCanary` quando TODOS os controles obrigatórios aplicáveis estiverem `Pass` e nenhum `Fail/Blocked/NotMeasured/NotPerformed` obrigatório permanecer.

2. **Gate de arquitetura (§47.1)**
   - agregar evidence de ADRs, diagramas/data flow, capability matrix, ausência de preview em caminho GA e ownership de serviços;
   - ausência ou drift de qualquer evidence obrigatório bloqueia readiness.

3. **Gate de segurança (§47.2)**
   - agregar evidence de threat model, secrets scan, SBOM/signatures, WDAC/Defender/patching, cross-tenant tests, incident response e pen-test;
   - `PenTestStatus != PassedIndependent` (ou equivalente já existente) deve manter o gate obrigatório como `Blocked/NotPerformed`; testes internos/SAST não satisfazem este requisito;
   - crítico/alto aberto bloqueia readiness.

4. **Gate de dados (§47.3)**
   - verificar hashes/manifests/lineage/evidence, privacy impact assessment, retention/deletion, backup/restore e corpus/fidelity report;
   - evidence ausente, adulterada ou stale falha fechado.

5. **Gate operacional (§47.4)**
   - dashboards/alerts, on-call/escalation, DLQ/retry/quarantine runbooks, capacity/FinOps, RTO/RPO exercitados e support package automation;
   - qualquer RTO/RPO ainda `Blocked/NotMeasured` deve impedir `ReadyForCanary`.

6. **Gate Microsoft 365 (§47.5)**
   - roles mínimas, tenant precheck, archive/licença/quota, AzCopy homologado, mapping validator, target root policy, limites 100 GB/500 linhas e treinamento do portal operator;
   - capability `Unknown/Blocked` nunca pode ser promovida a `Pass` por default.

7. **Evidence integrity / freshness**
   - todas as referências devem ser resolvidas server-side por tenant/project/build/policy version quando aplicável;
   - recomputar/validar digests e fingerprints persistidos antes de aceitar evidence canônica;
   - detectar supersession/drift: readiness antigo não continua válido após mudança relevante de build digest, policy version, capability matrix, security evidence, reconciliation certificate ou recovery evidence;
   - replay idêntico deve convergir deterministicamente.

8. **Readiness snapshot/report**
   - produzir snapshot/version imutável e auditável do review com build digest/commit SHA, policy/capability fingerprints, timestamp, correlation id e lista de blockers;
   - gerar view/report sanitizado que explique precisamente por que o sistema está ou não `ReadyForCanary`;
   - não armazenar secrets, SAS, tokens, paths sensíveis ou PII desnecessária.

9. **Workflow / RBAC**
   - qualquer ação de submit/acknowledge/approve relacionada ao review deve usar identidade/roles server-side; nenhuma role/actor fornecida pelo payload é confiável;
   - leitura/escrita deve ser tenant/project-scoped e anti-IDOR;
   - este Passo não autoriza aprovação humana final de go-live.

10. **Testes e gates**
   - testes unitários, arquitetura e integração SQL-real quando houver persistência;
   - cenários explícitos para: pen-test ausente, RTO/RPO não medidos, capability unknown, evidence stale/tampered, build digest alterado, cross-tenant, replay idêntico, concorrência e supersession;
   - `dotnet restore --locked-mode`;
   - build Release warnings-as-errors;
   - suíte completa;
   - `dotnet format --verify-no-changes`;
   - SCA/SBOM;
   - gitleaks/secret scanning;
   - runbook/doc gates existentes.

## Acceptance criteria mínimos

1. O sistema consegue materializar um Production Readiness Review reproduzível para um build/policy/capability state específico.
2. `ReadyForCanary` é impossível enquanto qualquer gate obrigatório estiver `Fail`, `Blocked`, `NotMeasured` ou `NotPerformed`.
3. Pen-test independente ausente nunca é interpretado como aprovado.
4. RTO/RPO não exercitados nunca são interpretados como aprovados.
5. Evidence adulterada/stale ou build/policy/capability drift invalida o snapshot anterior.
6. Cross-tenant/project é negado fail-closed e sem revelar existência.
7. Replay idêntico converge para o mesmo snapshot canônico; mudança material gera nova versão/supersession.
8. Nenhum segredo/PII proibida é persistido no readiness evidence/report.
9. Nenhum canário real, go-live ou encerramento de projeto é executado neste PR.
10. CI oficial do HEAD final fica 100% verde.

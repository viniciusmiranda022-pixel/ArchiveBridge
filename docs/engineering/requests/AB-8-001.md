# AB-8-001 — Slice 4A Passo 8

## Objetivo
Executar o Passo 8 do Vertical Slice 4A conforme `docs/engineering/vertical-slice-04a-control-plane-portal.md`: **hardening, testes de segurança, documentação e empacotamento on-premises**, sem iniciar Slice 4B.

## Fonte de autoridade
Use o roadmap/runbook/ADRs já aceitos, o histórico dos PRs #26, #29 e #30, e os requisitos não funcionais/critério de aceite do Slice 4A. Não introduza requisito novo nem altere decisões arquiteturais aceitas.

## Escopo obrigatório
1. Revisar e endurecer a superfície HTTP do Control Plane já implementada: autenticação/autorização fail-closed, antiforgery onde aplicável, headers de segurança, HTTPS fora de desenvolvimento local, cookies seguros, validação/limites de payload, output encoding, proteção IDOR/path traversal, correlação e mensagens sem stack trace.
2. Aplicar rate limiting às operações sensíveis já existentes no Slice 4A, sem criar novos write-paths.
3. Validar health checks distintos de liveness/readiness; readiness não pode declarar prontidão quando SQL Server ou dependência obrigatória estiver indisponível.
4. Fechar observabilidade já prevista: correlation ID por requisição, logs estruturados/sanitizados e métricas operacionais previstas, sem PII/segredo indevido.
5. Fechar testes automatizados de segurança/isolamento/concorrência necessários para os critérios de aceite do Slice 4A, incluindo autorização/RBAC, cross-tenant/cross-project/IDOR, antiforgery, idempotência, concorrência, CSV injection, hash/evidência, estados indisponíveis, Presentation Mode e retry.
6. Revisar UX operacional mínima prevista: teclado, labels acessíveis, contraste/estados/bloqueios acionáveis e paginação server-side onde o contrato já exige.
7. Atualizar documentação operacional e de segurança do Slice 4A, incluindo delta de threat model e runbook de implantação/operação on-premises.
8. Validar empacotamento on-premises compatível com a baseline aceita (IIS ou Windows Service/Kestrel conforme decisão existente), sem dependência obrigatória de Azure/SaaS.
9. Preservar migrations anteriores; qualquer migration nova deve ser aditiva, determinística, justificada e coberta pelo mecanismo de hash do repositório.
10. Executar gates completos: `dotnet restore --locked-mode`, build Release com warnings-as-errors, suíte completa contra SQL real quando aplicável, `dotnet format --verify-no-changes`, SCA/SBOM, gitleaks/secret scanning e validação documental/runbook.

## Fora do escopo
Nenhum `Export-EVArchive`, PST/libpff, split/repair, AzCopy, Azure staging, Purview job/import, Graph, Exchange Online, importação M365, reconciliação final ou qualquer funcionalidade de Slice 4B+.

## Regras de PR
- Branch dedicada a partir do `main` no merge confirmado do Passo 7 (`d963a658f2d862e9ea25d106981e733d8402ed00`).
- PR deve permanecer **Draft** durante a implementação.
- Não marcar Ready/não fazer merge sem `ARCHIVEBRIDGE_MERGE_APPROVED` para o HEAD corrente com CI totalmente verde.
- Reportar no PR o HEAD SHA, escopo implementado, testes/gates executados e qualquer limitação residual.

## Critério de encerramento
Passo 8 somente pode ser aprovado quando o escopo acima estiver implementado e validado, os gates obrigatórios estiverem verdes, não houver blocker/review thread pendente e o HEAD revisado permanecer estável. Slice 4B não deve ser iniciado neste PR.

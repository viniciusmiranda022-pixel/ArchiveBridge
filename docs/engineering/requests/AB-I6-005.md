# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I6-005

## I6 / EPIC-07 — Reconciliation — Passo 2: EXO Statistics Before/After & Observation Evidence Foundation

## Objetivo

Implementar o próximo incremento documentado do EPIC-07 após o `service result importer`: captura, normalização, persistência e revalidação **read-only** de estatísticas do Exchange Online Archive **before/after**, de forma tenant/project/wave/archive-scoped, versionada, idempotente e tamper-evident.

Este Passo fornece a evidência observacional necessária para o futuro `expected vs observed`, mas **não** produz ainda resultado final de reconciliação, disposition, certificate ou conclusão de wave/projeto.

## Fonte de autoridade

Use, nesta ordem: runbook, ADRs aceitos, governance, arquitetura já mergeada, work orders/PRs aceitos e threat models. Referências principais:

- `docs/runbook/06-parte-vi-plano-desenvolvimento.md` — I6/EPIC-07: `service result importer` → `EXO stats before/after` → `expected vs observed` → `exception disposition` → `certificate`;
- `docs/runbook/04-parte-iv-destinos-m365.md` §25.2, §25.9, §26.1, §26.2 e §26.4.

Não invente API, permissão ou semântica EXO/Graph não documentada/certificada. Se a infraestrutura atual não possuir adapter real certificado, implemente a porta e o boundary fail-closed sem promover fake/structural adapter a produção.

## Escopo obrigatório

1. Introduzir modelo Domain/Application para **EXO archive statistics observation** com fase explícita `BeforeImport` / `AfterImport`, vinculada server-side a `TenantScope + Project + Wave + TargetArchiveId`.
2. O caller fornece apenas identificadores opacos e metadados observacionais estritamente necessários. A mailbox/UPN/GUID/ArchiveRef canônica deve ser resolvida server-side a partir da wave/precheck/evidência persistida autorizada; nenhum alias/display mailbox vindo do caller é autoridade.
3. A captura deve ser estritamente **read-only**. Nenhum contrato deste Passo pode expor operação de mutação de mailbox/tenant.
4. `AfterImport` só pode ser aceito quando existir evidência canônica suficiente de que a importação Purview observada concluiu a etapa necessária para iniciar reconciliação. `Complete`/`ImportCompleted` continua sendo apenas evidência do provider e **não** fecha a wave/projeto.
5. `BeforeImport` deve representar o estado anterior real. Se a evidência existente de precheck não contiver todos os campos/folder statistics necessários, modele ausência como `Unknown/NotObserved`; nunca fabrique dados nem promova o precheck a snapshot completo sem prova.
6. Modelar somente campos necessários ao runbook, em tipos estruturados/locale-independent, incluindo quando efetivamente disponíveis:
   - `ArchiveStatus`, `ExchangeGuid`, `ArchiveGuid`;
   - `ItemCount`;
   - `TotalItemSizeBytes`;
   - `TotalDeletedItemSizeBytes`;
   - `LastLogonTimeUtc`;
   - `RetentionHoldEnabled`, `LitigationHoldEnabled`, `AutoExpandingArchiveEnabled` como observação read-only;
   - folder statistics relevantes: `FolderPath`, `FolderType`, `ItemsInFolder`, `ItemsInFolderAndSubfolders`, `FolderSizeBytes`, `FolderAndSubfolderSizeBytes`, `OldestItemReceivedDateUtc`, `NewestItemReceivedDateUtc`.
7. Ausência de campo do provider permanece explicitamente `Unknown/NotReported`; **nunca converter ausência para zero/false/default DateTime**.
8. Não parsear valores formatados/localizados por regex/string heurística. O adapter deve entregar valores estruturados; bytes/counts/dates precisam chegar tipados à Application/Domain.
9. Folder evidence deve ser bounded, deterministicamente ordenada/canonicalizada e deduplicada por identidade estável. Path/tipo inválido, duplicidade ambígua, excesso de linhas, campos oversized ou data temporalmente impossível devem falhar fechado.
10. Minimizar PII: não persistir subject/body/item content/attachment names. Persistir apenas mailbox/folder metadata necessária à reconciliação; logs/auditoria não devem registrar UPN/folder path bruto quando um ID/hash opaco for suficiente.
11. Persistir snapshots/evidence append-only, versionados por `scope + wave + archive + phase`, com hashes determinísticos de header e filhos. Toda reidratação que trate a evidência como canônica deve recomputar/revalidar child count + child hash + header hash; persistência é fronteira não confiável.
12. Idempotência/concorrência: mesma observação lógica converge para a mesma versão; mudança real gera nova versão; writers concorrentes idênticos convergem, e conteúdos realmente diferentes não podem ser colapsados em falso replay nem perdidos silenciosamente.
13. Anti-IDOR/RLS: cross-tenant/project/wave/archive e archive fora da seleção devem falhar fechado sem revelar existência, UPN, GUID ou detalhes do outro escopo.
14. Introduzir abstração substituível para coleta EXO (por exemplo `IExoArchiveStatisticsAdapter`) em Contracts. Domain/Application não podem depender de ExchangeOnlineManagement, PowerShell, Graph SDK, ASP.NET ou vendor SDK.
15. Se houver wiring/worker neste Passo, ele deve ficar desabilitado por padrão e falhar no startup quando configuração/capability obrigatória estiver ausente; nenhuma fallback permissiva.
16. Registrar auditoria sanitizada para capture/accept/reject/replay, com correlation/evidence IDs, sem raw PowerShell output, credencial, token, UPN desnecessário, folder path bruto desnecessário ou stack trace.
17. Atualizar threat-model/data classification/documentação operacional do I6 deixando explícito que EXO stats são **observações**, não resultado de reconciliação, e que holds nunca são alterados automaticamente.
18. Adicionar testes Domain/Application/Architecture/SQL-real cobrindo no mínimo:
   - happy path before e after;
   - after antes da evidência de conclusão do import => bloqueado sem chamar adapter;
   - archive fabricado/out-of-wave/cross-tenant/project => bloqueado sem sondagem;
   - `Unknown/NotReported` preservado sem virar zero/false/data mínima;
   - mesma evidência em ordem de folders diferente => mesmo hash lógico;
   - folder duplicado/oversized/malformado => fail-closed;
   - locale independente para bytes/counts/datas;
   - concorrência idêntica => uma versão lógica;
   - concorrência diferente => versões distintas/nenhuma perda;
   - tampering SQL de header, child count, child row, child hash e phase/archive identity => fail-closed em replay/latest;
   - nenhum código desta fatia consegue executar write em EXO/Graph;
   - nenhum content item/subject/body/attachment é persistido ou logado.
19. Executar todos os gates oficiais: restore locked, build Release warnings-as-errors, suíte completa com SQL Server real no CI, format, SCA/SBOM, gitleaks, migration hash/determinism, architecture tests e runbook conversion.

## Invariantes

- `AfterImport` só existe após evidência canônica de conclusão suficiente para iniciar reconciliação.
- EXO stats são observação read-only; não são `PASS`, `FAIL`, `PASS_WITH_EXPLAINED_EXCEPTIONS` ou certificate.
- ausência de dado não é zero.
- mailbox/archive identity é resolvida server-side.
- todo dado persistido é revalidado antes de ser tratado como canônico.
- holds/retention/auto-expansion são apenas observados; nunca alterados.
- Domain/Application permanecem vendor-independent.

## STOP-THE-LINE / fora do escopo

Este Passo NÃO autoriza:

- `Enable-Mailbox`, `Set-Mailbox`, auto-expansion ou qualquer write EXO/Graph;
- remoção/alteração de Retention Hold, Litigation Hold ou policy;
- criação/validação/início automático de import job Purview ou `Import data`;
- automação do portal Purview;
- `expected vs observed` final;
- outcomes finais `PASS`, `PASS_WITH_EXPLAINED_EXCEPTIONS`, `INCONCLUSIVE`, `FAIL` ou `DUPLICATE_RISK` como decisão da wave;
- exception disposition;
- certificate/evidence package final;
- conclusão de wave/projeto;
- decommission EV;
- I7 Hardening ou I8 Production Acceptance.

## Acceptance criteria mínimos

1. Um snapshot `BeforeImport` canônico e um `AfterImport` elegível podem ser capturados/persistidos read-only para archive autorizado.
2. `AfterImport` antes da evidência de conclusão necessária do import falha fechado e não chama o adapter.
3. Mailbox/archive usado pelo adapter é sempre resolvido server-side a partir do contexto autorizado.
4. Campos ausentes continuam `Unknown/NotReported`; nenhum default semântico é inventado.
5. Folder evidence é bounded, canonicalizada e determinística; mesma observação lógica produz mesmo hash independentemente de ordem de entrada.
6. Snapshot persistido revalida integralmente header + children + hashes/count antes de replay/latest.
7. Tampering de qualquer parte persistida falha fechado sem auto-correção/rewrite.
8. Replay idempotente e concorrência preservam uma única versão lógica para conteúdo idêntico e versões distintas para mudança real.
9. Cross-scope/out-of-wave falha indistinguivelmente de inexistente e não sonda adapter.
10. Nenhum write EXO/Graph/Purview, resultado final, disposition, certificate ou completion é introduzido.
11. Migrations históricas permanecem byte-for-byte intactas; qualquer nova migration é aditiva/determinística e passa nos hash gates.
12. CI oficial completo permanece verde.

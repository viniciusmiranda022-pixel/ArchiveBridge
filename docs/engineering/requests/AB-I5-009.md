# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I5-009

## I5 / EPIC-06 — Purview Adapter — Passo 3

## Objetivo

Implementar a fundação segura e reiniciável de **upload Purview Network Upload via AzCopy**, consumindo exclusivamente o SAS já aceito/custodiado no Passo 2 e os PSTs canônicos já produzidos/validados pelo pipeline. Este Passo cobre preparação de estrutura de upload, execução controlada do AzCopy, idempotência/retry/fencing, evidência sanitizada e verificação do resultado do transporte. Não cria nem inicia o import job no Purview e não gera ainda o mapping CSV oficial.

## Fonte de autoridade

Use, nesta ordem: roadmap/runbook do repositório, ADRs aceitos, governança, histórico de PRs aceitos e arquitetura-fonte. Em especial, `docs/runbook/04-parte-iv-destinos-m365.md` §§25.5–25.7: SAS tratado como segredo; AzCopy homologado por versão+SHA-256; `ProcessStartInfo.ArgumentList`; logs/plan em diretório controlado; worker dedicado; estrutura `ingestiondata/<project-wave>/...`; nenhum reuso de pasta entre projetos; criação/início do job permanece tarefa humana no portal Purview.

## Escopo obrigatório

1. Criar contratos Domain/Application vendor-independent para um upload request canônico e seu resultado/evidência, escopados a tenant/project/wave.
2. Resolver server-side a wave, os PSTs/parts canônicos e o `PurviewSasUploadHandle` vigente; nenhum path, URL SAS, storage host, filename ou project/wave scope vindo do caller pode ser tratado como autoridade.
3. Exigir que o SAS tenha sido aceito/custodiado para a MESMA wave e esteja em estado/lease válido no momento em que o upload worker o adquire. Usar exclusivamente o fluxo de claim/fencing aprovado no Passo 2; nunca aceitar SAS ad hoc no request de upload.
4. Construir a estrutura remota determinística conforme runbook: `ingestiondata/<project-wave>/...`, com prefixo canônico exclusivo por projeto/wave, nomes de PST derivados de evidência server-side, case preservado e sem traversal/absolute path/UNC/reparse.
5. Introduzir catálogo/configuração de AzCopy homologado contendo versão e SHA-256 esperados. Antes de qualquer execução, validar fail-closed a existência do binário e o hash exato; versão/hash desconhecidos ou divergentes bloqueiam.
6. Implementar adapter de processo isolado em Infrastructure/worker. Usar `ProcessStartInfo.ArgumentList`, nunca shell/string concatenada. Configurar `AZCOPY_LOG_LOCATION`, `AZCOPY_JOB_PLAN_LOCATION` e nível de log em diretório server-side dedicado por execução.
7. O SAS nunca pode aparecer em logs de aplicação, audit, problem details, telemetry, persisted command/evidence ou mensagens de exceção. O fato de o SAS aparecer inevitavelmente no command line do processo AzCopy deve ficar limitado ao worker dedicado conforme o runbook e documentado no threat model.
8. Persistir upload request/attempt/result de forma durável, append-oriented e tenant/project scoped. Retry/restart deve preservar lineage e nunca duplicar um upload lógico silenciosamente.
9. Aplicar job lease + fencing/heartbeat ao upload. Perda de lease/fencing durante a execução impede persistência de sucesso novo. Cleanup deve ser bounded e independente do cancellation token já cancelado.
10. Capturar apenas evidência sanitizada do AzCopy: exit code, timestamps, versão/hash do binário, quantidade/tamanho de arquivos esperados, correlation/request/attempt IDs e estado estruturado. Não persistir stdout/stderr bruto se puder conter SAS/path sensível; qualquer parser deve redigir URL/query e falhar fechado em formato inesperado.
11. Tratar `exit code != 0`, timeout, cancellation, binary mismatch, arquivo fonte ausente/tampered e perda de fencing como falha explícita; nenhum deles pode produzir `UPLOAD_VERIFIED`.
12. Antes de executar, revalidar fisicamente cada PST fonte contra manifesto/hash/tamanho canônico já persistido. Upload nunca deve partir de output stale/tampered.
13. Após sucesso do processo, produzir estado `Uploaded`/`UploadVerified` somente com evidência suficiente do próprio transporte. Não declarar importação Purview concluída; upload e import são estados distintos.
14. Garantir idempotência: mesma wave + mesmo conjunto canônico de parts + mesma geração SAS/destino + mesma policy/config deve convergir para a mesma identidade lógica; mudança real em qualquer componente produz nova identidade/attempt, nunca replay falso.
15. Preservar migrations históricas byte-for-byte. Qualquer migration nova deve ser aditiva, determinística, RLS/least-privilege e coberta pelo hash gate.
16. Atualizar threat model/runbook operacional para worker dedicado, exposição de command line, sanitização, trust boundary do SAS coletado manualmente e retenção dos logs/plan.
17. Executar todos os gates oficiais: restore locked, build Release warnings-as-errors, suíte completa com SQL real, format, SCA/SBOM, gitleaks, migration hashes e runbook conversion.

## Trust boundary específico deste Passo

O runbook vigente determina que o storage account é provisionado dinamicamente pelo Purview e só é conhecido quando o operador cria manualmente o import job e cola a URL SAS. Portanto, este Passo NÃO inventará pré-registro de storage account nem API externa de verificação inexistente.

O limite autorizado é:

- o SAS deve ter passado pela validação estrutural/custódia do Passo 2;
- o handle canônico deve estar vinculado server-side à mesma wave;
- o worker só pode adquirir a geração canônica daquele handle, via claim/lease/fencing;
- o request de upload não aceita URL/host/container arbitrários;
- a limitação de que validação estrutural não prova propriedade do storage account deve permanecer explicitamente documentada como dependência do procedimento humano do Purview, não mascarada como garantia técnica.

## STOP-THE-LINE / fora do escopo

Este PR NÃO autoriza:

- criação ou início de import job no Purview por API/automação;
- mapping CSV oficial;
- edição manual/Excel do CSV;
- Graph writes ou Exchange Online writes;
- `Enable-Mailbox -Archive`, auto-expansion ou mudanças de retention;
- reconciliação pós-import;
- marcação de wave/project como concluído apenas porque upload terminou;
- armazenamento do SAS em plaintext ou em logs;
- Azure Key Vault/Managed Identity como dependência obrigatória da baseline on-premises;
- reuso da pasta remota entre projetos/waves;
- qualquer execução contra destino não proveniente do handle SAS canônico da wave.

## Acceptance criteria mínimos

1. Caller não consegue escolher SAS, host, container, path remoto ou PST arbitrário; tudo é resolvido server-side sob TenantScope/Wave.
2. AzCopy só executa quando versão/hash do binário correspondem exatamente à configuração homologada.
3. `ProcessStartInfo.ArgumentList` é usado e não existe shell concatenando SAS/comando.
4. SAS não aparece em logs/evidence/exceptions persistidas; testes canary cobrem redaction de query/URL.
5. Fonte PST adulterada/ausente é detectada antes do processo e bloqueia upload.
6. Cross-tenant/project/wave e handle SAS de outra wave falham fechado sem revelar existência/segredo.
7. Retry/restart/concurrency preservam uma identidade lógica e attempt history; nenhum falso replay ou dupla conclusão.
8. Perda de job lease/fencing durante processo impede persistência de `UploadVerified`.
9. Exit code não-zero/timeout/cancellation nunca produzem sucesso.
10. Upload bem-sucedido persiste evidence sanitizada e estado distinto de importação/reconciliação.
11. Estrutura remota segue exatamente `ingestiondata/<project-wave>/...` e nunca reutiliza prefixo entre escopos distintos.
12. Migrations anteriores permanecem byte-for-byte intactas; nova migration, se necessária, passa RLS/least-privilege/hash gates.
13. CI oficial completo verde.

# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I5-001

## I5 / EPIC-06 — Purview Adapter — Passo 1: Capability Registry & Prechecks

## Objetivo

Iniciar o incremento documentado **I5 — Purview Adapter** implementando somente a fundação de capability discovery, tenant/mailbox prechecks e capacity/policy gates para o caminho GA de **Purview Network Upload**, antes de qualquer coleta de SAS, execução de AzCopy, geração de mapping CSV, criação/início de import job ou reconciliação.

## Fontes de autoridade

- `docs/runbook/04-parte-iv-destinos-m365.md` §§24, 25.1–25.4;
- `docs/runbook/06-parte-vi-plano-desenvolvimento.md`, I5 / EPIC-06;
- ADRs, threat model, tenancy/custody/audit/idempotency invariants e migrations policy vigentes;
- histórico aceito dos PRs #37–#39.

## Escopo obrigatório

1. Definir/implementar contratos Domain/Application equivalentes a `ITargetIngestor` para capability discovery e precheck sem acoplar Domain/Application a Graph, Exchange Online, PowerShell, Purview ou SDK vendor.
2. Modelar capability status com pelo menos `GeneralAvailability`, `Preview`, `Contractual`, `Unsupported` e `Unknown`; `Unknown` deve bloquear fail-closed.
3. Persistir capability evidence versionada e scoped a tenant/project/provider, incluindo fonte oficial, data observada, versão/documentação/capability version quando disponível e resultado de compatibilidade, sem inventar suporte.
4. Implementar tenant/mailbox precheck read-only por adapter substituível em Infrastructure, produzindo snapshot estruturado suficiente para as regras do runbook: mailbox identity resolvida, `ExchangeGuid`, `ArchiveGuid`, `ArchiveStatus`, `RecipientTypeDetails`, `AutoExpandingArchiveEnabled`, holds relevantes e estatísticas/capacidade quando disponíveis.
5. Nenhuma mudança de estado no tenant/mailbox pode ser executada implicitamente: `Enable-Mailbox -Archive`, auto-expansion, role assignment, PIM, Conditional Access ou qualquer mutação M365 ficam fora do escopo.
6. Implementar policy/capacity gate determinístico usando bytes estruturados e dados planejados existentes, sem parsing locale-dependent de strings formatadas.
7. Para archive imports, exigir `ArchiveStatus == Active`, parts dentro do limite da policy, `csvRowCount <= 500`, `TargetRootFolder != "/"`, bytes planejados dentro do `provider.mainArchiveImportLimitBytes` e dentro da capacidade observada menos margem de segurança.
8. `AutoExpandingArchiveEnabled=True` NÃO pode elevar `provider.mainArchiveImportLimitBytes`; acima do limite principal documentado o resultado deve ser `MICROSOFT_ASSESSMENT_REQUIRED` ou código equivalente fail-closed.
9. Implementar validação de target root: root `/` proibido; preparar contrato para root futuro `/ImportedPst_<Project>_<Wave>` sem gerar CSV neste Passo.
10. Garantir tenant/project/mailbox anti-IDOR e que identity/UPN/GUID usados pelo adapter sejam resolvidos server-side a partir do contexto autorizado.
11. Persistir precheck result/evidence de forma idempotente e append-oriented/versionada quando compatível com o modelo vigente; retries do mesmo input canônico não duplicam efeito lógico.
12. Sanitizar logs/erros: sem tokens, SAS, query strings, credenciais, transcript bruto, subject/body/recipients/attachments ou conteúdo de mailbox.
13. Tratar capability downgrade/contradição/staleness como bloqueio explícito até nova evidência válida; não promover Preview/Unknown para GA por heurística.
14. Migrations novas, se necessárias, devem ser aditivas, determinísticas e preservar migrations anteriores byte-for-byte.
15. Atualizar threat-model delta e documentação operacional para capability/precheck, incluindo quais operações são somente leitura e quais mutações ficam explicitamente proibidas.
16. Adicionar testes unitários, architecture e SQL real para isolamento, idempotência, capability status, capacity gates e tampering de evidence persistida.

## Acceptance criteria mínimos

1. Domain/Application não referenciam Graph/EXO/PowerShell/Purview SDK/vendor concreto.
2. `Unknown` e capability não-GA inadequada ao caminho selecionado bloqueiam fail-closed.
3. Capability evidence é versionada, auditável, tenant/project scoped e não pode ser reidratada como confiável se adulterada/inconsistente.
4. Precheck read-only produz snapshot estruturado e não altera mailbox/tenant.
5. Archive inactive bloqueia import archive.
6. `csvRowCount > 500` bloqueia.
7. `TargetRootFolder == "/"` bloqueia.
8. Part acima do limite da policy bloqueia.
9. Planned archive bytes acima do limite principal retornam assessment-required/bloqueio mesmo com auto-expansion ativo.
10. Planned bytes acima da capacidade observada menos safety margin bloqueiam.
11. Cross-tenant/project/mailbox é negado sem vazamento de existência.
12. Nenhum SAS/AzCopy/CSV/import job é criado ou executado neste Passo.
13. CI completo permanece verde no HEAD final.

## Testes obrigatórios

- capability `GeneralAvailability` válida passa o gate correspondente;
- `Unknown` bloqueia;
- `Preview` não é tratado como GA;
- capability evidence stale/downgraded/tampered falha fechado;
- archive inactive bloqueia;
- auto-expansion não amplia hard limit;
- 500 rows permitido e 501 bloqueado;
- root `/` bloqueado;
- part no boundary permitido e acima bloqueado;
- capacity margin respeitada;
- valores estruturados em bytes, sem parser locale-dependent;
- retry idempotente;
- cross-tenant/project/mailbox bloqueado;
- architecture tests de dependência;
- SQL real para persistence/concurrency/tampering;
- restore locked, build Release warnings-as-errors, format, SCA/SBOM, secret scanning e migration gates.

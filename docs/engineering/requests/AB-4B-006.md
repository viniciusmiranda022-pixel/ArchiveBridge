# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-4B-006

## Slice 4B — Passo 3: Partition Execution Foundation, Immutable Part Manifest & Restart Checkpoints

## Objetivo

Avançar o incremento I3/EPIC-04 documentado no runbook após o Partition Planning já mergeado, implementando a **fundação de execução de partição** apenas para planos que o sistema atual consegue provar de forma segura, com saída imutável, manifesto, lineage/custódia e restart/checkpoints duráveis.

Neste Passo, a execução autorizada é deliberadamente limitada ao caso já suportado pelo planner: `Planned / SinglePartWithinTarget`. Para esse caso, o part resultante deve representar exatamente os bytes do artefato fonte autorizado, materializados em output controlado, com hash próprio e manifesto. Planos `Unsupported` ou `Blocked` não executam. Não introduza parser/writer/splitter de fornecedor ainda; o split real multi-part continua dependente de engine/capability aprovada e de inventário suficiente.

## Fonte de autoridade

- `docs/runbook/03-parte-iii-conectores-e-engine-pst.md`, especialmente §20: política, identidade determinística, manifesto antes de validação, hard limit, `PartCreated` somente após sucesso, writer serial e regra de reabertura/reinspeção;
- `docs/runbook/06-parte-vi-plano-desenvolvimento.md`, I3/EPIC-04: planner, splitter, manifests, restart/checkpoints, immutable output, engine versioning;
- ADRs aceitos e decisões posteriores que retiraram vendor/parser não aprovado do caminho crítico;
- PRs #34 e #35 e seus work orders/decisões.

Quando houver conflito, ADR aceito e decisão mais recente do repositório prevalecem sobre exemplos antigos do runbook.

## Escopo obrigatório

1. Definir contratos de Domain/Application para executar um `PartitionPlan` canônico e persistido, sem dependência concreta de parser/vendor.
2. Aceitar execução **somente** de `PartitionPlanOutcome.Planned` com razão `SinglePartWithinTarget`, exatamente 1 part, `covers_entire_source=true`, size igual à origem e identidade determinística válida. Qualquer outro caso deve falhar fechado/retornar `Unsupported` sem criar output.
3. Resolver fonte, plano, tenant/projeto, paths e identidade sempre server-side a partir das stores/custódia; nunca aceitar path ou escopo do cliente.
4. Materializar o part em diretório de output controlado por `job/plan/part` ou equivalente já alinhado ao storage model, usando arquivo temporário + flush + rename/move atômico quando suportado. Nunca publicar part parcialmente escrito.
5. O part do caso `SinglePartWithinTarget` deve ser uma cópia byte-for-byte do artefato fonte autorizado; calcular SHA-256 durante/imediatamente após escrita e provar size/hash. O source original permanece intocado.
6. Reabrir/reinspecionar o output usando a capacidade read-only já existente antes de publicar `PartCreated`/estado equivalente. Se reabertura, hash, size ou inspeção falhar, não publicar sucesso.
7. Criar manifesto durável por part/conjunto contendo apenas metadados necessários e seguros: IDs opacos, source hash, plan hash, part key/sequence, size, output hash, engine/executor version, timestamps/correlation e lineage. Não incluir UPN completo, subject/body, attachment name, path absoluto real ou conteúdo de mensagens.
8. Persistir execution/checkpoint state de forma idempotente e concorrência-safe. Crash após temp-write, após hash, antes/depois do persist deve convergir sem duplicar part lógico nem publicar sucesso falso.
9. Implementar restart/replay: mesmo plan/part identity já concluído e cuja evidência/hash ainda conferem deve retornar o resultado canônico; saída divergente/stale/tampered deve falhar fechado e exigir disposição, nunca sobrescrever silenciosamente.
10. Aplicar containment/path safety/reparse checks em source e output; output path deve ser derivado de IDs opacos e permanecer sob raiz configurada. Não seguir symlink/junction/reparse conhecido.
11. Respeitar resource limits/cancellation/timeout/disk-space preflight aplicáveis. Falha de espaço, cancelamento ou I/O nunca gera `PartCreated` canônico.
12. Preservar tenant/project isolation, RLS e anti-IDOR nas stores/read models novos.
13. Se schema novo for necessário, migration deve ser aditiva, determinística, com grants mínimos e hashes anteriores imutáveis. Preferir tabelas/ledger append-only para execution attempts/manifests/checkpoints; não reescrever migrations já mergeadas.
14. Atualizar threat-model delta, classificação de dados e runbook operacional do Slice 4B.
15. Adicionar testes unitários/arquitetura/integração para os critérios abaixo e executar todos os gates do repositório.

## Acceptance criteria mínimos

1. `SinglePartWithinTarget` canônico produz exatamente um output imutável cujo SHA-256 e size fecham com os bytes realmente escritos.
2. Source permanece byte-for-byte inalterado.
3. Output só vira canônico após write completo + flush/close + hash + reabertura/reinspeção + persistência de manifesto/checkpoint bem-sucedidos.
4. `Unsupported`/`Blocked`, plano não canônico, forged identity, cross-tenant/project ou source stale => zero part canônico e zero efeito externo.
5. Replay idempotente do mesmo plan retorna o mesmo part/manifest sem duplicar saída lógica.
6. Concorrência de duas execuções do mesmo plan converge para um único resultado canônico.
7. Crash/restart simulado em ao menos estes boundaries é seguro: após temp file, após rename/finalization, após persist de checkpoint antes de retorno. Não pode existir falso sucesso nem duplicidade lógica.
8. Tampering do output após conclusão é detectado no replay/readback e falha fechado; não sobrescrever automaticamente.
9. Temp file órfão não é confundido com part concluído e pode ser limpo/reconciliado por regra segura/documentada.
10. Manifesto não contém path absoluto, mailbox/UPN completo, subject/body, attachment name, SAS/segredo ou bytes de conteúdo.
11. Domain/Application permanecem independentes de parser/vendor e ASP.NET.
12. Migrations anteriores permanecem byte-for-byte; nova migration, se houver, passa migration hash/determinism e least-privilege grants.
13. CI completo verde no HEAD final.

## Testes obrigatórios

- happy path single-part materialization + hash/size + byte equality;
- source unchanged;
- `Unsupported`/`Blocked` => zero output;
- forged/noncanonical plan => fail-closed;
- stale source/hash divergence => fail-closed antes de publicar output;
- cross-tenant/cross-project anti-IDOR;
- replay same plan => same canonical part/manifest;
- same plan concurrent execution => one logical canonical result;
- cancellation/timeout and insufficient-space/I/O failure => no canonical success;
- simulated orphan temp file + restart;
- simulated crash after final file creation but before canonical checkpoint + reconciliation without duplicate;
- output tamper/hash mismatch on replay => fail-closed;
- unsafe/symlink/reparse output/source path => fail-closed where platform primitive exists;
- persisted manifest has no sensitive path/content fields;
- migration hashes prior to this Passo remain stable.

# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I6-001

## I6 / EPIC-07 — Reconciliation — Passo 1: Service Result Importer & Evidence Foundation

## Objetivo

Iniciar o incremento documentado **I6 — Reconciliation / EPIC-07** após o fechamento do EPIC-06 Purview. Este Passo implementa a fundação de ingestão e custódia dos resultados do serviço Purview gerados pelo workflow humano já definido no runbook, permitindo registrar e revalidar de forma determinística a identidade do import job e as evidências de validation/result por PST **sem automatizar a criação, validação ou início do job no portal**.

A ordem vem das fontes de autoridade: `docs/runbook/04-parte-iv-destinos-m365.md` §25.9/§26 e `docs/runbook/06-parte-vi-plano-desenvolvimento.md` §43.2/§44 (`I6 - Reconciliation`; EPIC-07 inicia por `service result importer`).

## Fonte de autoridade

Use, nesta ordem: runbook, ADRs aceitos, governance, arquitetura já mergeada, work orders/PRs aceitos e threat models. Não invente API Purview que não esteja documentada/certificada. A criação e o início do import job continuam **humanos no portal Purview**.

## Escopo obrigatório

1. Introduzir modelo Domain/Application para uma **Purview import run observation/evidence** vinculada server-side a `TenantScope + Project + Wave` e à cadeia canônica já existente de upload/mapping.
2. O caller pode fornecer somente os valores originados do workflow humano que necessariamente surgem fora do ArchiveBridge (por exemplo nome/ID do Purview job, horário observado, código/status do serviço e arquivo/relatório anexado). Toda wave, upload, mapping version/hash, expected PST set, target root e mailbox correlation devem ser resolvidos/revalidados server-side.
3. Antes de aceitar evidência de serviço, exigir que a wave possua:
   - upload canônico `Uploaded/UploadVerified` coerente com a manifestação per-file;
   - mapping CSV canônico publicado, íntegro e correspondente à mesma wave/evidência;
   - nenhum drift posterior de binding/execution/upload/mapping.
4. Modelar **planned job name** determinístico conforme a regra já documentada para o portal (somente minúsculas, números, hífen e underscore). O nome planejado deve ser derivado server-side e vinculado à wave antes de aceitar provider observation.
5. Registrar `provider_operation_id`/Purview job ID somente como evidência observada após a criação humana do job; ele não substitui a chave lógica interna. Replays devem convergir; tentativa de reassociar a mesma wave/planned job a provider ID incompatível deve falhar fechado.
6. Implementar importer para **validation report / service result** como artefato não confiável, versionado, imutável e hashado. Parsing deve ser estrito e bounded (tamanho/linhas/campos/encoding), nunca executar conteúdo e nunca confiar em path/nome de arquivo do caller.
7. Normalizar somente os campos necessários para reconciliação descritos no runbook: identidade do PST/remote name, status por PST, imported size/count e skipped/corrupted quando efetivamente fornecidos pelo serviço. Campo não fornecido permanece `Unknown/NotReported`; nunca inventar zero.
8. Cada item de resultado deve correlacionar 1:1 com a manifestação de upload + mapping canônicos da mesma wave. Item desconhecido, duplicado, nome divergente, conjunto extra/ausente quando o formato afirma completude, ou cross-wave deve falhar fechado/inconclusivo conforme semântica explícita — nunca ser silenciosamente descartado.
9. Persistir snapshots/evidence append-only, tenant/project/wave-scoped, com hash determinístico e revalidação completa na reidratação. Persistência é fronteira não confiável: tampering de header, provider ID, job name, hashes, status ou filhos deve falhar fechado.
10. Idempotência/concorrência: o mesmo artefato/observação lógica deve convergir para a mesma versão; conteúdo realmente diferente gera nova versão ou conflito explícito conforme a semântica do resultado. Nenhuma mudança real pode ser colapsada em falso replay.
11. Registrar auditoria sanitizada para anexação/aceitação/rejeição da evidência, sem CSV bruto, SAS, UPN desnecessário, path local, conteúdo de mensagem ou stack trace.
12. Introduzir uma primeira avaliação de **evidence completeness do provider** apenas para o material deste Passo. Ela pode indicar `CompleteForProviderEvidence`, `Incomplete` ou `Inconclusive`, mas **não** pode produzir `PASS`, `PASS_WITH_EXPLAINED_EXCEPTIONS` nem encerrar a wave, pois EXO before/after, expected-vs-observed, dispositions e certificate pertencem aos próximos Passos do EPIC-07.
13. Atualizar threat-model do I6, documentação operacional e data classification, deixando claro que validation/result reports são input externo não confiável e que `Complete` no portal Purview não encerra o projeto.
14. Adicionar testes Domain/Application/Architecture/SQL-real para happy path, anti-IDOR/cross-scope, replay idempotente, concorrência, report truncado/malformado/oversized, item duplicado/desconhecido, remote name divergente, provider ID reassociado, mapping/upload drift, tampering SQL e ausência de campos opcionais sem conversão para zero.
15. Executar todos os gates vigentes do repositório: restore locked, build Release warnings-as-errors, suíte completa com SQL Server real no CI, format, SCA/SBOM, gitleaks, migration hash/determinism e runbook conversion.

## Invariantes

- `Complete`/`Analysis completed`/`Import completed` no Purview é apenas evidência do provider, nunca encerramento automático da wave/projeto.
- `provider_operation_id` é dado observado; a identidade lógica permanece server-side e determinística.
- validation/result report é dado hostil/não confiável.
- nenhum resultado pode ser associado a PST/mailbox por ordem, posição, filename de planejamento ou input arbitrário do caller; usar somente a cadeia `WaveEntry ↔ Binding ↔ PartitionExecution ↔ Upload manifest ↔ Mapping` já aceita.
- `Unknown` permanece `Unknown`; ausência de métrica não é zero.
- evidência é append-only/tamper-evident e isolada por tenant/project/wave.

## STOP-THE-LINE / fora do escopo

Este PR NÃO autoriza:

- automação do portal Purview;
- criação, validação, salvamento ou início automático de import job;
- clique/execução automática de `Import data`;
- scraping/browser automation do Purview;
- Graph/EXO writes, `Enable-Mailbox`, alteração de hold/retention/auto-expansion;
- coleta real automatizada de EXO post-import stats (próximo incremento do EPIC-07);
- cálculo final expected-vs-observed entre origem e EXO;
- disposition/aprovação de exceções;
- emissão/assinatura do certificado final;
- marcar wave/projeto `COMPLETED`;
- decommission/freeze/retention change no EV;
- iniciar I7 Hardening.

## Acceptance criteria mínimos

1. Uma wave com upload + mapping canônicos pode receber uma observação de job/result Purview e produzir evidência persistida, versionada e auditável sem automatizar o portal.
2. Planned job name é server-side/determinístico; provider job ID observado não altera a chave lógica e não pode ser reassociado silenciosamente.
3. Validation/result report é parseado bounded/fail-closed e seu SHA-256 participa da evidência.
4. Cada resultado por PST correlaciona exatamente com o conjunto canônico da wave; ambiguidades não viram sucesso.
5. Reexecução idêntica converge; mudança real não é perdida sob concorrência.
6. SQL tampering de qualquer campo material/header/filho/hash falha fechado na leitura/replay.
7. Campo de métrica ausente continua `Unknown/NotReported`, não `0`.
8. O máximo que este Passo produz é completeness do provider evidence; nenhum `PASS` final/certificate/completion é alcançável.
9. Domain/Application permanecem independentes de browser automation/Purview SDK/EXO/Graph/vendor concreto.
10. Migrations anteriores permanecem byte-for-byte; novas, se necessárias, são aditivas/determinísticas e passam pelos hash gates.
11. CI oficial completo permanece verde.

# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I5-004

## I5 / EPIC-06 — Purview Adapter — Passo 2: Secure SAS Intake & Custody

## Objetivo

Implementar o próximo incremento documentado do adapter Purview: **entrada segura, validação, custódia temporária e ciclo de vida do SAS do Network Upload**, preservando a baseline on-premises e preparando o contrato para o upload worker, **sem executar AzCopy neste Passo**.

## Fontes de autoridade

- `docs/runbook/04-parte-iv-destinos-m365.md` §§25.5–25.6;
- `docs/runbook/06-parte-vi-plano-desenvolvimento.md`, I5 / EPIC-06;
- ADR-0003 (baseline on-premises);
- ADR-0006 (Purview Network Upload + exceção controlada do SAS em argv somente no AzCopy futuro);
- ADR-0008 (isolamento/segredos on-premises; perfil inicial nó único/DPAPI; HA de segredos `BLOCKED_PENDING_EVIDENCE`);
- invariantes de tenancy, anti-IDOR, audit, idempotency, redaction e migrations já aceitos;
- PR #40 / `AB-I5-001..003` como precondição funcional de capability/prechecks.

## Escopo obrigatório

1. Definir contratos Domain/Application para intake e custody do SAS sem acoplar Domain/Application a DPAPI, Windows APIs, Purview SDK ou Azure Key Vault.
2. O request deve referenciar apenas identificadores opacos/scoped (tenant/project/wave); a wave e o contexto Purview devem ser resolvidos server-side antes de aceitar o segredo.
3. O SAS deve entrar por superfície marcada como secreta: nunca echoar o valor, nunca persistir plaintext em SQL e nunca incluí-lo em analytics, tracing, structured logs, exceptions, audit payloads ou telemetry.
4. Validar a URL antes da custódia, fail-closed, incluindo no mínimo:
   - esquema `https`;
   - host compatível com o destino Purview/Storage autorizado pelo capability/evidence vigente, sem aceitar host arbitrário por string heurística;
   - container/path `ingestiondata` conforme o runbook;
   - presença e validade temporal de expiry;
   - permissões mínimas esperadas para upload, sem aceitar permissões mais amplas quando a policy vigente as proibir;
   - rejeição de URL malformada, fragment, userinfo, esquema alternativo, path inesperado ou parâmetros críticos ausentes/duplicados/ambíguos.
5. Canonicalizar somente metadados não secretos necessários para evidence/audit. A query completa, assinatura e token SAS nunca podem ser retornados ou persistidos fora do secret store.
6. Implementar `ISecretStore`/contrato equivalente substituível e adapter inicial **single-node on-premises com DPAPI**, protegido pela identidade dedicada do workload. Não implementar Azure Key Vault/Managed Identity como dependência obrigatória.
7. O perfil HA/multi-node de segredos deve permanecer explicitamente `BLOCKED_PENDING_EVIDENCE`; não criar fallback inseguro, key file compartilhado ou pseudo-HA.
8. Persistir apenas um handle opaco/metadata record no SQL, tenant/project/wave-scoped, contendo estado, fingerprint não reversível, timestamps, expiry, key/version metadata quando aplicável e linkage de auditoria. Nunca persistir o SAS plaintext/ciphertext no SQL se o secret store não exigir esse modelo.
9. O segredo deve ter lifecycle explícito: `Stored -> Available -> Consumed/Expired -> Destroyed` (ou equivalente), com transições determinísticas e idempotentes. Expired/Destroyed nunca volta a `Available` sem novo intake explícito.
10. Apenas o identity boundary do futuro `ArchiveBridge-UploadWorker` pode ler/obter o segredo. Control/API não deve possuir método de leitura plaintext para UI/operador após intake.
11. Preparar operação de `AcquireForUpload`/lease equivalente com uso único/reuso controlado conforme policy, sem executar processo externo neste Passo. Toda leitura deve ser autorizada por tenant/project/wave e por workload identity.
12. Após consumo final, expiração ou cancelamento explícito da wave, permitir destruição local segura do material secreto e registrar apenas evidência de lifecycle. Não prometer revogação remota do SAS no serviço Microsoft.
13. Implementar redaction central para qualquer string/URI que possa conter query SAS, inclusive logs de validação, model binding errors, exceptions e telemetry. Testes de canary devem falhar se o segredo aparecer em output observável.
14. Evitar exposição acidental via `ToString`, debugger display, serialization automática, model validation dump ou problem details. Tipos secretos devem ser non-serializable/redacted por desenho quando aplicável.
15. Implementar proteção contra replay/cross-scope: handle de um tenant/project/wave não pode ser usado em outro; novo SAS para mesma wave deve versionar/invalidar o anterior de forma explícita e auditável.
16. Implementar concorrência segura para intake/replace/destroy/acquire; nenhuma race pode resultar em dois segredos ativos canônicos quando a policy exigir um único ativo.
17. Atualizar threat-model delta, data classification e runbook operacional deste Passo, incluindo risco de process inspection futuro e a exceção restrita do argv reservada exclusivamente ao Passo AzCopy.
18. Migrations novas, se necessárias, devem ser aditivas/determinísticas e preservar migrations anteriores byte-for-byte.
19. Executar restore locked, build Release warnings-as-errors, suíte completa, format, SCA/SBOM, gitleaks/secret scanning, migration hash gates e validação documental.

## Acceptance criteria mínimos

1. Um SAS válido para uma wave autorizada pode ser recebido sem ecoar o segredo e gerar um handle opaco persistido.
2. SQL, audit, logs, traces, exceptions, telemetry e responses não contêm a query/signature/token SAS.
3. Host/path/container/scheme/expiry/permissões inválidos ou ambíguos são rejeitados fail-closed.
4. O secret material é protegido por adapter single-node DPAPI sob abstraction; Domain/Application não referenciam DPAPI/Windows/Azure SDKs.
5. O perfil HA de segredos permanece bloqueado e não existe fallback multi-node improvisado.
6. Apenas o boundary autorizado do upload worker consegue adquirir o secret; UI/API/control não consegue reler plaintext.
7. Expiração/destruição impede nova aquisição; re-intake exige nova versão explícita.
8. Cross-tenant/project/wave e stale handles são negados sem revelar existência.
9. Intake concorrente produz um único estado canônico conforme policy e preserva histórico/auditoria.
10. Destruição local não é representada como revogação remota no Purview/Microsoft Storage.
11. Testes de canary demonstram ausência do SAS em logs, problem details, exception messages e evidence payloads.
12. Nenhum AzCopy/processo externo/upload real é iniciado neste Passo.
13. CI completo verde no HEAD final.

## Testes obrigatórios

- URL HTTPS válida no host/container autorizado;
- HTTP, userinfo, fragment, path/container errado, host não autorizado e query SAS malformada bloqueiam;
- expiry expirada/próxima demais conforme policy bloqueia;
- parâmetros críticos duplicados/ambíguos bloqueiam;
- fingerprint estável do mesmo segredo sem permitir reconstrução;
- secret nunca aparece em serialization/`ToString`/problem details/log sink de teste;
- DPAPI round-trip no adapter sob identity/context de teste suportado e falha segura quando proteção não está disponível;
- SQL real para isolation, idempotency, concurrency, replace, destroy e stale handle;
- cross-tenant/project/wave bloqueado;
- acquire por workload não autorizado bloqueado;
- expired/destroyed não readquire;
- migration/hash gates;
- architecture tests de dependência.

## STOP-THE-LINE / fora do escopo

Este Passo NÃO autoriza:

- execução de `azcopy.exe` ou qualquer processo externo de upload;
- colocar SAS em command line neste PR;
- upload/staging real no container Microsoft;
- Azure Key Vault ou Managed Identity como baseline obrigatória;
- habilitar perfil HA/multi-node de segredos;
- geração/validação de mapping CSV;
- criação/validação/início de Purview import job;
- Graph writes ou Exchange Online writes;
- reconciliação/post-import;
- logar/transmitir/copiar SAS para ticket, e-mail, documento ou transcript;
- avanço para o próximo Passo dentro deste PR.

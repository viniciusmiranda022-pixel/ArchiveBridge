# AB-6B-001 — Slice 4A Passo 6B — Upload de Mapping CSV no Control Plane

## Base autorizada

- `main`: `60f2ad2a541052689d1d509790f95b34174f9d19`
- Passo 6A já mergeado: backend seguro de recepção/validação de CSV.
- Este incremento conecta o Portal/Razor Pages ao backend 6A.

## Escopo

Implementar a superfície HTTP/Portal para upload e validação de `mapping.csv`, reutilizando `ValidateMappingCsvUploadUseCase` e `IMappingValidationStore` existentes.

### Invariantes obrigatórios

- Tenant/projeto sempre derivados do principal autenticado via `IPortalScopeAccessor`; nunca aceitar escopo vindo do cliente.
- `UserId`, `RequestedBy` e correlação derivados server-side.
- RBAC server-side: apenas `Operator` e `Administrator` podem submeter CSV. `Viewer`, `Auditor` e `Approver` permanecem sem autorização para essa ação.
- Presentation Mode continua estritamente read-only: POST de upload deve retornar 403 antes de qualquer SQL/store/auditoria de negócio.
- Feature gate de deployment para a superfície de upload, default `false`; usuário sem RBAC recebe 403 sem inferir o estado do gate; usuário autorizado com gate off recebe 503.
- Antiforgery obrigatório.
- HTTP/multipart deve ser bounded; não confiar em `Content-Length`. O backend 6A permanece a autoridade final de tamanho e deve continuar aplicando `EffectiveMaxUploadBytes` e `AbsoluteMaxUploadBytes = 50 MiB`.
- Nenhum byte bruto de CSV deve ser persistido pela aplicação. Buffer temporário do framework, se utilizado, deve ser estritamente transitório e documentado; não gravar em evidence root/landing/staging ou outro storage da aplicação.
- Nenhum mailbox/path/PST/cell value deve aparecer em logs, auditoria ou mensagens estruturadas de erro.
- Reutilizar a evidência canônica persistida no replay idempotente.
- Nenhuma migration nova é esperada para 6B. Migrations 0001–0018 devem permanecer byte-for-byte iguais.
- Nenhum `Export-EVArchive`, PST, PowerShell, AzCopy, Purview, Graph ou importação M365.
- Não iniciar Slice 4B, Passo 7 ou Passo 8.

## UX/HTTP

A tela `Pages/Mapping/Index` existente deve deixar de ser apenas visual em modo normal e ganhar code-behind real.

### GET

- Em Presentation Mode: preservar dataset sintético e controles de upload desabilitados; nenhum acesso SQL para a ação de upload.
- Em modo normal: resolver escopo autenticado; listar ondas do projeto usando leitura já existente; apresentar apenas ondas elegíveis (`Approved`/`Frozen`) no seletor, sem transformar a filtragem visual em autorização.
- Gerar `IdempotencyKey` server-side por formulário/GET.
- Exibir o limite efetivo real configurado, não hardcode `5 MiB` se houver configuração diferente.
- Se `validationId` estiver presente, carregar o resultado canônico via `IMappingValidationStore.GetAsync(scope, validationId)`; cross-tenant/cross-project/inexistente => 404.

### POST

Criar handler explícito para validação de CSV, preferencialmente `OnPostValidateCsvAsync`.

Entrada permitida do navegador deve se limitar a:

- `waveId`
- `contentCodePage`
- `idempotencyKey`
- arquivo CSV

Não bindar tenant/project/user/correlation/requestedBy do formulário.

Fluxo obrigatório:

1. Presentation Mode guard => 403 e zero efeitos.
2. Resolver identidade e escopo do principal fail-closed.
3. RBAC server-side Operator/Administrator.
4. Feature gate.
5. Validar GUIDs/input básico.
6. Aplicar limites HTTP/multipart coerentes com o hard max; backend continua bounded e autoritativo.
7. Chamar `ValidateMappingCsvUploadUseCase` com stream não confiável e metadados server-side.
8. Auditar resultado operacional sem conteúdo/PII de mapping.
9. Usar PRG: redirecionar para GET da Mapping page com `validationId` canônico.

### Mapeamento de resultado/erro

- Valid / Invalid / Rejected recebidos e custodiados => PRG para o resultado canônico; `Invalid`/`Rejected` são resultado de validação, não falha HTTP.
- arquivo ausente / extensão/nome/declared length inválidos => 400.
- tamanho excedido => 413.
- onda inexistente/cross-scope => 404, sem diferença observável anti-IDOR.
- onda em estado não autorizado => 409.
- conflito de idempotência => 409.
- RBAC negado => 403.
- feature gate desabilitado para principal autorizado => 503.

## Resultado no Portal

Exibir apenas dados seguros/canônicos:

- Validation ID
- Outcome (`Valid`, `Invalid`, `Rejected`)
- SHA-256
- SizeBytes
- RowCount quando disponível
- IssueCount / IssuesTruncated
- Issues estruturadas: linha, coluna, código, mensagem genérica

Nunca renderizar bytes brutos, mailbox, caminho, PST ou valor de célula.

- idempotency-conflict

Não usar filename, mailbox/path/PST/cell values como `reason`, `resourceId` ou mensagem de auditoria. Preferir `validationId`/`waveId`/códigos fechados.

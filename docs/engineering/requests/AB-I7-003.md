# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I7-003

## I7 — Hardening — Passo 2: Performance, Capacity & SLO Baseline

## Objetivo

Dar continuidade ao I7 documentado no roadmap após o fechamento dos gates de resilience/recovery/chaos, transformando os requisitos de **performance, capacity e SLO** já descritos no runbook em um baseline executável, reproduzível e fail-closed para os fluxos reais implementados em I0–I6.

Este Passo NÃO autoriza declarar Production Ready, não estabelece SLA comercial e não inventa metas numéricas ausentes da fonte de autoridade.

## Fonte de autoridade

Usar, nesta ordem:

1. `docs/runbook/06-parte-vi-plano-desenvolvimento.md` — I7 Hardening, §45 Test Strategy, §46 Performance e dimensionamento, §47 Production Readiness;
2. ADRs e governance aceitos;
3. work orders/PRs aceitos I0–I6 e I7 Passo 1;
4. arquitetura e implementação corrente do repositório.

Quando o runbook disser explicitamente que um número é estimativa/típico e não SLA, preserve essa natureza. Não converter estimativa em gate rígido sem evidência aprovada.

## Escopo obrigatório

### 1. Harness de benchmark reproduzível

Criar um harness automatizado e versionado para medir, no mínimo, os caminhos implementados e testáveis sem dependência de ambiente externo de cliente:

- hash/streaming de artefatos PST/custódia;
- inspeção PST usando o adapter atualmente disponível no repositório;
- partition execution no caminho suportado atual;
- geração/validação de mapping CSV;
- persistência/replay dos stores SQL mais críticos do pipeline;
- reconciliation/certificate em datasets sintéticos autorizados.

O harness deve registrar versão do build, runtime, host profile, tamanho do dataset, seed, número de iterações, warmup e timestamp da execução.

### 2. Métricas mínimas

Coletar de forma estruturada e sem PII/segredos:

- wall-clock duration;
- throughput bytes/s e/ou items/s quando semanticamente aplicável;
- CPU process time quando disponível;
- peak working set quando disponível;
- bytes lidos/escritos quando medíveis de forma confiável;
- SQL operation latency/throughput para operações escolhidas;
- erro/cancelamento/resource-limit outcome.

Não armazenar assunto, corpo, destinatários, anexos ou nomes reais de mailbox nos resultados de benchmark.

### 3. Perfis e capacity planning

Materializar os perfis de worker descritos no runbook como **perfis de referência**, explicitamente marcados como estimativas e não mínimos garantidos:

- Inspector: 8 vCPU / 32 GiB / 512 GiB scratch;
- Heavy PST: 16–32 vCPU / 64–128 GiB / 1–2 TiB NVMe/SSD;
- Validator: 4–8 vCPU / 16–32 GiB / 256–512 GiB;
- Upload: 4–8 vCPU / 16 GiB / cache mínimo.

Implementar/validar a fórmula documentada de scratch:

`sourceCopyBytes + expectedPartBytes + repairBackupBytes + engineTemporaryOverhead + safetyMargin(20%)`

onde aplicável ao domínio atual. Se algum termo ainda não existir na implementação (ex.: repairBackup), representar explicitamente como zero/não aplicável somente quando a operação não o utiliza; não esconder capacidade futura necessária.

### 4. Budget e fail-closed

Antes de iniciar operações locais que já conhecem o footprint necessário, validar capacity budget de forma determinística quando o código atual permitir essa prova.

- falta de scratch/capacidade deve falhar antes de efeito parcial quando possível;
- nenhuma execução pode converter `Unknown` de capacidade em `Enough` por default;
- valores negativos, overflow, unidade ambígua ou arithmetic overflow devem falhar fechado;
- cálculos devem usar tipos inteiros apropriados e testes de boundary.

Não introduzir uma nova engine de repair/split apenas para satisfazer esta seção.

### 5. SLO evidence model

Criar uma representação versionada de **SLO evidence / performance baseline**, separando claramente:

- `ObservedMetric` — medição obtida;
- `ReferenceEstimate` — referência/estimativa do runbook;
- `ContractualSla` — NÃO CONFIGURADO neste projeto, a menos que já exista fonte explícita aceita;
- `GateStatus` — `Measured`, `NotMeasured`, `NotApplicable`, `BlockedByExternalDependency` ou equivalente já consistente com a modelagem do projeto.

A taxa Microsoft de aproximadamente 24 GB/dia por mailbox deve permanecer registrada somente como **typical/reference, not SLA**. Não usar esse número como promessa, SLA ou critério de aprovação automático.

### 6. Regressão de performance

Adicionar mecanismo de comparação entre baseline e execução atual que:

- produza relatório determinístico;
- não falhe CI por ruído de host compartilhado usando thresholds inventados;
- permita detectar regressões graves apenas quando existir um critério explícito e versionado;
- caso não exista critério aprovado, reporte delta como evidência informativa, sem promover/falhar automaticamente.

Se o repositório já tiver política de benchmark CI, reutilize-a.

### 7. Datasets

Usar datasets sintéticos/reprodutíveis. Para tamanhos grandes, sparse files podem ser usados apenas para testar capacidade/I/O quando não houver parsing semântico; o runbook é explícito que sparse file sozinho não valida parser PST.

Cobrir pelo menos classes pequenas e boundaries relevantes que sejam viáveis em CI. Cenários 100–500+ GB não devem ser simulados como prova de parser se o CI não executar bytes reais suficientes; registre-os como `BlockedByEnvironment`/evidência pendente quando aplicável.

### 8. Documentação

Adicionar/atualizar:

- performance baseline report;
- capacity planning guide;
- SLO evidence matrix;
- threat-model delta apenas se novos componentes/telemetria forem introduzidos;
- instruções reproduzíveis para rodar benchmarks localmente e em host dedicado.

Documentação deve distinguir claramente **medido**, **estimado**, **não medido**, **bloqueado** e **não aplicável**.

### 9. Testes

Adicionar testes unitários/integração/arquitetura para, no mínimo:

- capacity formula e safety margin de 20%;
- overflow e valores extremos;
- unknown capacity fail-closed;
- serialização/determinismo dos resultados;
- redaction/sanitização de resultados;
- comparação de baseline sem thresholds implícitos;
- persistência/replay se houver store novo;
- isolamento tenant/project se qualquer evidência for persistida por escopo.

### 10. Gates de qualidade

Executar todos os gates já existentes do repositório:

- restore locked-mode;
- build Release com warnings-as-errors;
- testes unitários, arquitetura e integração SQL-real;
- format verify;
- SCA/SBOM;
- gitleaks/secret scanning;
- migration/runbook integrity gates.

## Acceptance criteria mínimos

1. Existe harness reproduzível para os caminhos locais/SQL relevantes já implementados.
2. Resultados incluem metadata suficiente para comparação e são sanitizados.
3. A fórmula de scratch do runbook está implementada/testada onde aplicável e trata overflow/unknown fail-closed.
4. Perfis de worker do runbook são representados como referências, não como mínimos garantidos.
5. O valor ~24 GB/dia/mailbox permanece marcado como típico/referência, nunca SLA.
6. Nenhum threshold de CI ou SLO é inventado sem fonte versionada.
7. Cenários não executáveis em CI são marcados explicitamente como não medidos/bloqueados, não como aprovados.
8. Nenhum benchmark usa dados reais/PII/segredos.
9. Nenhuma migration histórica é alterada; novas migrations, se necessárias, são aditivas/determinísticas e passam gates de hash.
10. CI oficial permanece 100% verde.

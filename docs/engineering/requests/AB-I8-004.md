# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I8-004

## I8 — Production Acceptance — Passo 2: Production Canary Acceptance & Evidence

## Objetivo

Implementar o gate executável, auditável e fail-closed para o **canário de produção** documentado no runbook §48. Este Passo deve permitir planejar, autorizar, acompanhar e registrar evidências do canário usando exatamente o mesmo build/digest candidato a produção, sem fabricar evidência externa e sem promover o sistema a go-live por ausência de dados.

O canário real somente pode ser iniciado quando existir um `Production Readiness Review` canônico e vigente com resultado `ReadyForCanary`. Se pen-test, RTO/RPO, capability, licença/quota, operador, tenant controlado ou qualquer outro gate obrigatório continuar `Blocked/NotMeasured/NotPerformed/Fail`, o canário deve permanecer bloqueado.

## Fontes de autoridade

- `docs/runbook/06-parte-vi-plano-desenvolvimento.md` §§43.2, 47, 48 e 49;
- `AB-I8-001` e correções `AB-I8-002/003`;
- cadeia canônica de I6 reconciliation/certificate;
- evidências de I7 hardening/recovery/security/performance;
- capability registry, Purview prechecks, upload/mapping/reconciliation já aceitos.

## Escopo obrigatório

1. **Canary plan model**
   - criar identidade opaca e tenant/project-scoped para um plano de canário;
   - vincular explicitamente `ReadinessSnapshotId`, build digest/commit SHA, policy version e capability fingerprint canônicos;
   - o plano deve ser imutável/versionado após autorização;
   - drift em qualquer uma dessas dependências invalida/supersede o plano anterior.

2. **Gate de entrada**
   - resolver o Production Readiness Review exclusivamente server-side;
   - somente `ReadyForCanary` vigente pode permitir transição para `Authorized`;
   - `Fail/Blocked/NotMeasured/NotPerformed`, evidence stale/tampered ou fingerprint divergente bloqueiam antes de qualquer efeito externo;
   - actor/roles vêm exclusivamente do contexto autenticado server-side; anti-IDOR obrigatório.

3. **Matriz obrigatória do canário (§48)**
   Materializar, com identidade estável e status explícito, os cenários documentados:
   - tenant controlado e mailbox de teste licenciada;
   - corpus com 20 tipos de item/propriedades customizadas;
   - PST pequeno;
   - PST no boundary de 18 GB;
   - replay do mesmo PST no mesmo target root;
   - tentativa deliberada com target root diferente deve bloquear;
   - corrupção conhecida deve resultar em quarantine;
   - crash recovery;
   - reconciliação + evidence package;
   - restore/rollback operacional;
   - approval para primeira onda real de baixa criticidade.

4. **Estados e semântica fail-closed**
   - cada cenário deve possuir estados equivalentes a `Pending`, `Running`, `Pass`, `Fail`, `Blocked`, `NotPerformed` quando aplicável;
   - `Unknown`, ausência de resultado externo, timeout ou resposta ambígua nunca viram `Pass`;
   - resultado agregado `CanaryPassed` somente quando TODOS os cenários obrigatórios aplicáveis estiverem `Pass` e a cadeia de evidência continuar íntegra e vigente;
   - qualquer falha material ou blocker mantém `CanaryPassed = false`.

5. **Same-build promotion invariant**
   - o build/digest usado no canário deve ser exatamente o candidato promovível;
   - mudança de commit SHA, artifact digest, policy version ou capability fingerprint após início do canário invalida a promoção e exige novo canário;
   - não existe fork de “canary build” e “production build”.

6. **Evidence ingestion / custody**
   - registrar referências opacas para evidências de cada cenário, nunca SAS/token/secret/raw PII;
   - validar digests/fingerprints de artefatos persistidos antes de tratá-los como canônicos;
   - evidência deve ser append-only/tamper-evident e replay idêntico deve convergir;
   - resultado externo deve preservar source/timestamp/correlation/provenance suficiente para auditoria.

7. **Canary execution boundary**
   - este PR pode implementar contratos/orquestração/gates e adapters de evidência necessários ao canário;
   - CI e testes não devem chamar tenant M365/EV real nem depender de credenciais reais;
   - nenhuma evidência externa ausente pode ser simulada como produção;
   - execução real contra tenant/mailbox controlados só é permitida quando readiness estiver `ReadyForCanary`, credenciais/roles autorizadas existirem e a ação usar os adapters/capabilities já homologados.

8. **Replay / duplicate safety**
   - replay do mesmo PST no mesmo target root deve demonstrar comportamento idempotente conforme o pipeline canônico;
   - target root divergente para o mesmo artifact/mailbox deve bloquear fail-closed;
   - nenhuma execução de canário pode duplicar efeito externo em retry/restart/lease reclaim.

9. **Crash / rollback / recovery evidence**
   - integrar as evidências de recovery já existentes; não declarar sucesso apenas por teste sintético desconectado;
   - crash durante processamento deve convergir sem perda de evidência nem efeito duplicado;
   - restore/rollback operacional deve permanecer `Blocked/NotPerformed` quando não houver drill compatível e comprovado.

10. **Reconciliation / evidence package**
   - canário não pode passar sem reconciliation certificate canônico e vigente para os artifacts envolvidos;
   - `INCONCLUSIVE`, `FAIL`, `DUPLICATE_RISK`, incomplete evidence ou disposition não resolvida impedem `CanaryPassed`;
   - evidence package deve referenciar a cadeia canônica usada no julgamento.

11. **Approval da primeira onda real**
   - modelar a aprovação final do canário como decisão humana auditável e server-side RBAC;
   - essa aprovação apenas autoriza avançar para a etapa de operational readiness/go-live; não marca projeto/wave como `COMPLETED`;
   - nenhum payload pode fornecer actor/role confiável.

12. **Persistência, concorrência e integridade**
   - SQL-real quando houver persistência;
   - concorrência deve convergir deterministicamente para um único estado/version canônico;
   - tampering de status, fingerprints, evidence refs ou resultados deve falhar fechado;
   - migrations históricas são imutáveis; novas alterações de schema devem ser aditivas.

13. **Testes e gates**
   Cobrir explicitamente:
   - readiness não pronto bloqueia autorização sem efeito externo;
   - readiness superseded/drift invalida plano;
   - mesmo build/digest preservado vs alterado;
   - todos os 10 cenários do §48 presentes;
   - unknown/ambiguous external result não vira pass;
   - replay mesmo PST/mesmo root converge;
   - root diferente bloqueia;
   - corrupção conhecida -> quarantine;
   - crash/retry sem duplicação;
   - reconciliation/evidence package incompleto bloqueia;
   - cross-tenant/project negado;
   - actor/role spoofing negado;
   - concorrência/replay/tampering SQL-real.

   Executar ainda:
   - `dotnet restore --locked-mode`;
   - build Release com warnings-as-errors;
   - suíte completa unit/architecture/contracts/integration;
   - `dotnet format --verify-no-changes`;
   - SCA/SBOM;
   - gitleaks/secret scanning;
   - gates de documentação/runbook existentes.

## Acceptance criteria mínimos

1. Um canário não pode ser autorizado sem um readiness snapshot canônico `ReadyForCanary` e vigente.
2. Os dez cenários documentados do §48 estão materializados e auditáveis.
3. `CanaryPassed` é impossível enquanto qualquer cenário obrigatório estiver `Fail`, `Blocked`, `Pending`, `Running`, `NotPerformed` ou sem evidência verificável.
4. O mesmo build/digest do canário é obrigatório para promoção; qualquer drift invalida a promoção.
5. Replay mesmo PST/mesmo root é idempotente e target root divergente bloqueia.
6. Corrupção conhecida produz quarantine, nunca sucesso silencioso.
7. Crash/retry/restart não duplica efeito nem perde evidência.
8. Reconciliation certificate/evidence package canônicos são pré-requisito para sucesso do canário.
9. Aprovação humana usa identidade/roles server-side e não conclui automaticamente o projeto.
10. Evidência ausente, stale, tampered ou externa não comprovada permanece fail-closed.

## STOP-THE-LINE

Este Passo **não** autoriza declarar `ProductionReady`, `GoLive` ou `COMPLETED`; não autoriza primeira onda real de cliente fora de um canário controlado; não autoriza decommission EV; não autoriza contornar `Blocked/NotMeasured/NotPerformed`; não autoriza fabricar pen-test/RTO/RPO/licença/quota/canary evidence; e não autoriza criar o próximo PR antes do merge deste.

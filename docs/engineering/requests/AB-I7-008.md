# ARCHIVEBRIDGE_ENGINEERING_REQUEST

REQUEST_ID: AB-I7-008

## I7 — Hardening — Passo 4: Security Hardening, Supply-Chain & Production Security Evidence

## Objetivo

Fechar a parcela ainda documentada do **I7 — Hardening** relacionada a **WDAC/App Control, hardening dos workers Windows, supply-chain security, incident-response exercitado e preparação verificável para pen-test**, transformando requisitos do runbook em controles executáveis/evidência fail-closed. Este Passo não declara Production Ready nem substitui um pen-test independente.

## Fontes de autoridade

- `docs/runbook/05-parte-v-seguranca-infra-operacao.md` §§30–37 e §47.2;
- `docs/runbook/06-parte-vi-plano-desenvolvimento.md` I7 / §§43.2, 45 e 47;
- threat models, ADRs, CI e decisões já aceitas no repositório;
- histórico dos PRs I7 #49, #50 e #51.

## Escopo obrigatório

1. **Windows worker hardening baseline**
   - materializar uma baseline versionada e verificável para workers Windows cobrindo, no mínimo: SO suportado/patching, Defender for Endpoint/tamper protection, App Control for Business/WDAC allowlist, Secure Boot/vTPM/Credential Guard quando aplicável, BitLocker, SMBv1/TLS legado desabilitados, RDP deny-by-default, service identity least-privilege, scratch ACL sem execute para dados, outbound restrito e crash-dump handling;
   - distinguir claramente `Required`, `Unsupported`, `NotMeasured` e `Blocked`; ausência de evidência nunca vira `Pass`;
   - não assumir controles Azure-only em hosts on-premises sem capability comprovada.

2. **WDAC/App Control evidence**
   - definir modelo de policy evidence/digest/version para a allowlist usada pelos workers;
   - validar que executáveis críticos aprovados (ArchiveBridge worker, AzCopy homologado e demais binários explicitamente permitidos pelo roadmap) sejam identificados por publisher/hash/path rule conforme política documentada, sem allow-all genérico;
   - adicionar testes que rejeitem binário/versão/hash não autorizado e policy evidence adulterada;
   - nenhuma policy deve ser aplicada automaticamente em produção neste PR; apenas geração/validação/evidence e, quando seguro, teste local/sintético.

3. **Supply-chain hardening executável**
   - preservar `dotnet restore --locked-mode`, deterministic Release build, gitleaks, SCA/SBOM e demais gates atuais;
   - adicionar/fechar validação de provenance/manifest dos artifacts produzidos quando ainda ausente no caminho atual;
   - garantir que artifact/build identity seja derivável por SHA/digest e que drift entre build aprovado e promoted artifact falhe fechado;
   - nenhum pacote/binário pode ser baixado/executado por versão flutuante sem digest/publisher/capability fixados.

4. **Security regression suite**
   - consolidar testes automatizados para authz/RBAC, cross-tenant isolation, secret redaction, path traversal/canonicalization, queue/payload poisoning, tamper evidence e privilege spoofing já implementados;
   - adicionar gaps comprováveis encontrados durante a revisão deste Passo, sem duplicar testes meramente cosméticos;
   - cada cenário deve demonstrar explicitamente `deny/fail-closed`, ausência de vazamento de segredo/PII e ausência de efeito externo indevido.

5. **Incident-response exercise evidence**
   - implementar um exercício reproduzível e não destrutivo para pelo menos: secret-leak canary, hash mismatch/tampering e cross-tenant denial;
   - materializar outcome, timestamps, correlation/evidence digest e disposition operacional sem armazenar segredo/PII;
   - incident exercise não pode alterar dados reais de cliente nem criar side-effect externo.

6. **Pen-test readiness — sem alegação falsa**
   - gerar checklist/evidence bundle interno com escopo, attack surface, trust boundaries, test identities/fixtures sintéticas, known blocked items e hashes da build alvo;
   - status deve permanecer `NotPerformed/Blocked` até existir relatório independente real;
   - nunca marcar `Pass` ou “pen-test concluído” baseado somente em testes internos/SAST.

7. **Security readiness model**
   - persistir/derivar um resultado de readiness tamper-evident que só possa ficar `Pass` para os controles efetivamente exercitados deste Passo;
   - itens externos/institucionais (pen-test independente, WDAC aplicado em imagem de produção, MDE tenant policy real etc.) devem permanecer `NotMeasured/Blocked` quando não houver evidence real;
   - readiness geral do projeto NÃO pode virar `ProductionReady` neste Passo.

8. **Threat-model e documentação**
   - atualizar delta do threat model para App Control/WDAC, supply chain, build promotion, incident response e pen-test boundary;
   - documentar procedimentos operacionais sem inserir segredo, URL assinada, token ou path sensível;
   - registrar claramente o que permanece pendente para o I8.

9. **Testes e gates**
   - testes unitários, arquitetura e integração necessários;
   - SQL-real quando houver persistência/evidence store;
   - `dotnet restore --locked-mode`;
   - build Release com warnings-as-errors;
   - suíte completa;
   - `dotnet format --verify-no-changes`;
   - SCA/SBOM;
   - gitleaks/secret scanning;
   - runbook/doc gates existentes.

## Acceptance criteria mínimos

1. Nenhum controle de hardening ausente ou não exercitado é reportado como `Pass`.
2. WDAC/App Control policy evidence possui identidade/digest/version, detecta tampering e rejeita artifact/binário não autorizado.
3. Build/promoted artifact possui identidade determinística verificável; drift de SHA/digest falha fechado.
4. Secret redaction regression injeta canaries e prova que logs/evidence não persistem SAS/token/Authorization/cookie/PII proibida.
5. Cross-tenant e privilege-spoofing regressions permanecem fail-closed.
6. Pelo menos três incident-response drills sintéticos produzem evidence auditável sem side effects externos.
7. `PenTestStatus` permanece `NotPerformed/Blocked` sem relatório independente real.
8. Nenhum endpoint/write-path de produção novo é criado apenas para satisfazer o hardening.
9. Migrations históricas permanecem byte-for-byte inalteradas; qualquer migration nova é aditiva, determinística e coberta pelos gates de hash existentes.
10. CI oficial do HEAD final fica 100% verde.

## STOP-THE-LINE / fora do escopo

Este Passo NÃO autoriza:

- declarar `Production Ready`, `GoLive`, canário aprovado ou I8 concluído;
- alegar pen-test institucional/independente sem relatório real;
- aplicar WDAC em hosts reais de produção automaticamente;
- alterar GPO/Defender/Intune/Entra/Azure Policy de cliente;
- abrir inbound/RDP/SMB ou relaxar firewall/ACL para testes;
- armazenar segredo, token, SAS, Authorization header, subject/body/attachment name ou path sensível em evidence;
- introduzir Azure PaaS obrigatório incompatível com a baseline já aceita;
- iniciar I8 dentro deste PR.
